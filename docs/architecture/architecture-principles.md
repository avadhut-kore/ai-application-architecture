# AI Application Architecture Principles

This document defines the 17 core architectural principles governing all systems, modules, and reference implementations within the **`ai-application-architecture`** repository. 

Adherence to these principles is mandatory. Every pull request and architecture review is validated against these tenets.

## Principle 1 — LLM Output is Untrusted Data

### Architectural Statement
Output generated by foundation models (LLMs/SLMs) is stochastic, unpredictable, and inherently untrusted. It must never be treated as valid domain entities, safe HTML, or executable commands without validation.

### Rationale
Models hallucinate, deviate from instructions, omit required keys, and are susceptible to prompt injection payloads embedded in retrieved external data. Ingesting raw LLM strings into databases, SQL queries, or frontend DOMs introduces severe vulnerabilities (OWASP LLM02).

### Implementation Rules
* **Strict Schema Parsing**: All structured model outputs must be validated using schema enforcement libraries (Pydantic in Python, Zod in TypeScript, strongly typed record serializers in .NET).
* **Sanitization**: Strip escape characters, enforce whitelist formatting, and validate range constraints.
* **Fail-Safe Fallback**: If parsing fails after configured retry attempts, throw explicit domain exceptions or route to human review.

```python
# GOOD: Validated domain entity parsing
try:
    response = await llm_provider.generate_structured(prompt, schema=InvoiceExtractionSchema)
    validated_invoice = DomainInvoice.from_schema(response)
except SchemaValidationError as ex:
    logger.warning("Model failed schema validation", exc_info=ex)
    return await fallback_routing_service.handle_failure(prompt, ex)

# BAD: Blindly trusting LLM output
raw_text = await llm_provider.generate(prompt)
db.execute(f"INSERT INTO invoices VALUES ('{raw_text}')")  # SQL Injection & Malformed Data Hazard
```

## Principle 2 — Business Rules Must Not Depend Solely on Probabilistic Output

### Architectural Statement
Core business rules, financial ledger transactions, compliance validations, and authorization checks must be enforced by deterministic code, not delegated to model discretion.

### Rationale
An LLM can be coaxed, confused, or drift across versions. Asking an LLM *"Is this user authorized to transfer $10,000?"* or *"Calculate the total tax for this transaction"* introduces non-deterministic risk into mission-critical systems.

### Implementation Rules
* The LLM may suggest an action, formulate an explanation, or extract parameters from unstructured input.
* The deterministic domain layer must validate permissions, verify account balances, calculate math, and execute business invariants.

## Principle 3 — AI Provider Abstraction Must Prevent Vendor Lock-In

### Architectural Statement
The core application and business domain must have zero compile-time or runtime dependencies on proprietary vendor SDKs (`openai`, `anthropic`, `google.generativeai`).

### Rationale
Foundation model pricing, performance, and availability fluctuate rapidly. Tying application logic directly to vendor-specific SDK idioms cripples architectural agility and prevents local offline execution.

### Implementation Rules
* Define port interfaces in `building-blocks/` (`ILlmProvider`, `IEmbeddingProvider`, `IVectorStore`).
* Vendor SDKs live exclusively within infrastructure adapters (`infrastructure/providers/openai/`, `infrastructure/providers/ollama/`).
* Application services receive provider instances via Dependency Injection.

## Principle 4 — Deterministic Logic Must Remain Deterministic

### Architectural Statement
Never use an AI model to perform operations that can be accomplished reliably, faster, and cheaper with deterministic algorithms, regular expressions, or relational queries.

### Rationale
Invoking a 70-billion-parameter neural network to compute mathematical sums, sort JSON arrays, validate email formats, or filter records wastes compute, increases latency by orders of magnitude, and introduces failure modes into simple tasks.

### Anti-Pattern vs. Correct Pattern
* **Anti-Pattern**: Prompting an LLM: *"Here is a list of numbers: 12, 4, 89, 2. Please sort them in ascending order."*
* **Correct Pattern**: Parse numbers with regex/JSON parser and execute native sorting (`sorted(numbers)`).

## Principle 5 — Agents Must Operate Within Explicit Permissions and Tool Boundaries

### Architectural Statement
Autonomous agents must execute within strictly circumscribed permission envelopes with least-privilege toolsets, parameter schemas, and bounded execution cycles.

### Rationale
An unbounded agent with open-ended tool access can trigger infinite execution loops, incur exorbitant token costs, corrupt database states, or execute unintended side effects when encountering confusing inputs.

### Implementation Rules
* Every tool must expose an explicit, immutable JSON Schema defining its parameters.
* Every agent execution loop must enforce hard limits on:
  * Maximum iterations (e.g., maximum 8 tool calls per turn).
  * Maximum execution time (timeout).
  * Maximum accumulated token budget.
* Read-only tools may execute autonomously; write/destructive tools require authorization tokens or human approval.

## Principle 6 — Memory is a Distinct Architectural Capability (Not RAG)

### Architectural Statement
Conversation memory and state persistence represent distinct architectural capabilities with unique access patterns, lifecycle policies, and consistency models, and must not be conflated with Knowledge Retrieval (RAG).

### Rationale
* **RAG**: Statistically retrieves static, external, factual knowledge chunks based on semantic similarity.
* **Memory**: Maintains temporal, conversational, episodic, or working state for a specific user, session, or agent across turns. Conflating them results in unstructured vector dumping and loss of conversational context.

### Memory Hierarchy
1. **Working Memory**: Current context window (active prompt, recent messages, active scratchpad).
2. **Short-Term / Session Memory**: Redis or key-value store holding conversation history for the active session.
3. **Episodic / Long-Term Memory**: Curated, summarized user preferences and historical interactions stored in structured entity stores.

## Principle 7 — RAG is a Knowledge Retrieval Pattern, Not Synonymous with an AI Agent

### Architectural Statement
Retrieval-Augmented Generation (RAG) is an information retrieval and context-synthesis pattern. It is not an autonomous agent.

### Rationale
A RAG pipeline is a pipeline: $\text{Query} \rightarrow \text{Retrieve} \rightarrow \text{Augment} \rightarrow \text{Generate}$. It does not possess agency, does not select dynamic tools, and does not iterate toward an open-ended goal. Labeling simple RAG pipelines as "Agents" obscures the architectural differences in testing, failure modes, and operational complexity.

## Principle 8 — Tools are Capabilities Exposed to Models/Agents

### Architectural Statement
Tools are well-defined, stateless capabilities exposed to models via structured interfaces. They must be designed like enterprise microservices.

### Implementation Rules
* **Idempotency**: Read-only tools must be idempotent. Mutating tools must support idempotency keys.
* **Schema Contract**: Tools must declare unambiguous descriptions, typed parameters, and strict return schemas.
* **Error Transparency**: Tool execution failures must return structured, informative error messages back to the model rather than crashing the execution process.

---

## Principle 9 — Workflows and Agents are Different Architectural Constructs

### Architectural Statement
Deterministic workflows and autonomous agents solve distinct architectural problems and must not be conflated:

* **Workflow**: A predefined, deterministic directed acyclic graph (DAG) or state machine where transitions between steps are governed by explicit code and business logic.
* **Agent**: A non-deterministic reasoning loop where the foundation model dynamically decides which step or tool to invoke next based on intermediate observations.

```
DETERMINISTIC WORKFLOW:
Step A ────────► Step B ────────► [Condition ?] ──Yes──► Step C
                                        │
                                        No ─────────────► Step D

AUTONOMOUS AGENT LOOP:
            ┌─────────────────────────────────────────┐
            ▼                                         │
State ──► Model Reason ──► Select Tool ──► Observe ───┘ (Iterates until model decides to stop)
```

**Rule**: Prefer deterministic workflows wherever the sequence of tasks is known in advance. Reserve autonomous agents for open-ended problem exploration.

## Principle 10 — Every Autonomous Behavior Must Have Measurable Evaluation Criteria

### Architectural Statement
No autonomous agent or probabilistic AI feature may be deployed without an automated, reproducible evaluation suite.

### Implementation Rules
* Define quantitative evaluation metrics:
  * **Goal Completion Rate**: Percentage of runs where the agent achieved the requested business objective.
  * **Trajectory Accuracy**: Number of tool calls required vs. optimal path.
  * **Tool Parameter Correctness**: Rate of valid tool invocations without schema errors.
* CI/CD pipelines must execute evaluations against benchmark datasets and block regressions.

---

## Principle 11 — Human-in-the-Loop Should Be Treated as a First-Class Architecture Pattern

### Architectural Statement
Autonomous systems must incorporate human review, intervention, and approval as native, asynchronous architectural capabilities—not as afterthoughts.

### Implementation Rules
* High-consequence actions (fund transfers, data deletions, contract dispatch) must transition to a `PENDING_HUMAN_APPROVAL` state.
* The architecture must support durable state suspension and resumption (e.g., via durable orchestrators or message queues) while waiting for human authorization.

---

## Principle 12 — AI Systems Must Be Observable

### Architectural Statement
AI applications must implement distributed tracing, semantic metrics, and structured logging across every prompt, retrieval, model invocation, and tool execution.

### Implementation Rules
* Standardize on **OpenTelemetry GenAI Semantic Conventions**.
* Every span must capture:
  * Model identifier and provider endpoint.
  * Token usage (prompt tokens, completion tokens, cached tokens).
  * Latency (TTFT and duration).
  * Temperature and configuration parameters.
* PII and sensitive data must be redacted before telemetry export.

---

## Principle 13 — Model Quality and System Quality are Separate Concerns

### Architectural Statement
An enterprise AI system must achieve high reliability, safety, and operational excellence even when the underlying foundation model produces variable or imperfect outputs.

### Rationale
Model providers update weights, encounter degradation, and occasionally hallucinate. Relying solely on "better models" to fix systemic bugs is an architectural anti-pattern. System quality is achieved through robust parsing, retries, guardrails, fallback providers, and deterministic validation layers.

---

## Principle 14 — Cost and Latency are Architectural Concerns

### Architectural Statement
Token consumption and response latencies directly impact enterprise viability and must be addressed during architectural design, not patched in production.

### Implementation Rules
* **Streaming**: Interactive user experiences must use chunked streaming to deliver low Time-to-First-Token (TTFT).
* **Semantic Caching**: Cache identical or semantically equivalent embeddings and prompt queries to avoid duplicate inference.
* **Context Budgeting**: Dynamically trim, summarize, and prioritize context windows to avoid wasting tokens on irrelevant background data.

---

## Principle 15 — Local Development and Production Share Architectural Boundaries

### Architectural Statement
The architectural boundaries, interfaces, and component interactions of an application must be identical whether running locally against Ollama or in production against enterprise cloud endpoints.

### Implementation Rules
* A developer running `docker compose up` on a laptop executes the exact same domain code and application services as the production Kubernetes cluster.
* Only the configuration and infrastructure adapters differ (e.g., swapping `OllamaLlmAdapter` with `AzureOpenAiLlmAdapter`).

---

## Principle 16 — State and Context Isolation Across Executions

### Architectural Statement
Cross-tenant and cross-session context must be strictly isolated at the storage, retrieval, and prompt construction layers.

### Implementation Rules
* Vector queries must enforce tenant-level partition filters (`tenant_id = X`) at the database query level, never post-filtered in application memory.
* System prompts and agent memory scratchpads must be cleared or freshly initialized for distinct sessions to prevent prompt leakage across user boundaries.

---

## Principle 17 — Graceful Degradation Under Model Failure

### Architectural Statement
When foundation model providers encounter rate limits, outages, or excessive latency, the application must degrade gracefully without catastrophic system failure.

### Implementation Rules
* Implement circuit breakers to detect provider outages and stop sending failing traffic.
* Support multi-provider fallback routing (e.g., if Cloud Provider A returns HTTP 503, route request to Cloud Provider B or local fallback model).
* Return cached, static, or degraded responses with clear user notifications when all model providers are unavailable.
